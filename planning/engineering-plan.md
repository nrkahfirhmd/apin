# Engineering Plan — Apin v1.1 (Cycle 2: hardening + open-decision closure)

Generated by `/plan` (the `planner` subagent) from `planning/spec.md` (unchanged since cycle 1,
still carries 5 open questions) and `memory/` (decisions, technical-debt, coding-standards, apis,
database-schema, sprint-summary, ADRs). This overwrites the cycle-1 `planning/engineering-plan.md`
and is the input to `/tasks`, which will regenerate `tasks/task-graph.md`.

## How to read this plan

Cycle 1 shipped 18/21 backlog items (all Must + Should) with QA passing 107 tests, 0 lint
violations, a clean build, and a confirmed simulator launch — but QA explicitly called the build
**not release-ready**. This cycle is deliberately a **hardening/completion cycle, not a rewrite**:
no new architecture, no new requirements beyond what `planning/spec.md` already states. The
backlog below has three tiers, in priority order:

1. **Close the four carried-forward release-readiness gaps** in `memory/technical-debt.md`.
2. **Resolve (or re-confirm) the four open product/UX decisions** logged in `memory/decisions.md`
   that cycle 1 implemented as assumptions rather than confirmed calls, plus the 5 still-open
   spec questions.
3. **Sequence the cycle-1 deferred backlog** (T15 inline Siri/Spotlight spike, T20 tagging, T21
   weekly digest/streak) behind the above.

**Important environment constraint, stated explicitly per this cycle's brief:** several items
below can only be genuinely completed with physical Apple Intelligence–capable hardware and/or an
active Apple Developer account for live Instruments/CloudKit/Siri verification — **this dev
environment has neither.** Those items are marked "Requires real hardware" in the backlog table.
If Kv cannot make hardware/account access available during this cycle, those items should be
expected to carry forward to cycle 3 as debt again, the same way they carried into this cycle —
that is an acceptable, explicitly-tracked outcome, not a planning failure. Items marked "No" are
fully buildable and verifiable in this dev environment (simulator + unit tests) and should not be
blocked on hardware availability.

Architecture, coding standards, and testing conventions from cycle 1 are **kept as the standing
convention for this cycle and are not re-derived here** — see `memory/coding-standards.md` (naming,
structure, style, testing, commit conventions) and the Architecture decisions section below, which
only records what's *new or changed* for cycle 2.

## Architecture decisions

No new architecture this cycle — SwiftData + `ApinCore` local package + App Group
(`group.com.apin.app`) + CloudKit (`ModelConfiguration(cloudKitDatabase: .automatic)`) as
established in cycle 1 (see `memory/database-schema.md`, `memory/adrs/001-*`,
`memory/adrs/002-*`) remain the baseline and are not being revisited. The only architecture-level
decisions this cycle adds are narrow, scoped to the four debt fixes:

- **Duplicate-`id` handling is a repository-level responsibility, not a schema-level constraint**
  — rationale: `@Attribute(.unique)` was already removed in T18 because SwiftData's CloudKit
  mirroring doesn't support it, and that trade-off isn't being reopened. Instead,
  `SwiftDataJournalRepository.fetch(by:)`/`delete(id:)` (item 1) must stop silently taking
  `.first` when multiple entries share an `id` and instead handle the multi-match case explicitly
  (e.g. return/act on all matches, log, or reconcile by `createdAt` recency — task-runner's call
  during `/tasks`, but it must be a deliberate, tested behavior, not an implicit `.first`). A
  startup or periodic dedup pass is the mitigation for entries that already diverged, not a
  replacement for fixing the read/delete paths themselves.
- **Debug-only capability override must be compiled out of release builds** — rationale: item 3's
  override switch exists purely to unblock manual QA of a Must-have negative path (Req 7) without
  real disqualifying hardware; it must be `#if DEBUG`-gated (or equivalent) so it can never be
  triggered in a shipped build, and its existence/usage should be documented in-file so `/review`
  can verify the gate is real, not cosmetic.
- **Hardware-dependent verification items (4, 5, 10) are treated as gated, not skippable** — if
  Kv cannot provide device/account access during this cycle, the correct outcome is to leave the
  corresponding `memory/technical-debt.md` entries open with an updated note (attempted, still
  blocked) rather than mark them silently done or quietly drop them from the plan. `/qa` should
  treat "verified blocked, documented" as a passing state for these three items specifically, same
  as cycle 1 did for the same underlying gaps.
- **Decision-confirmation items (6, 7, 8) are content/product decisions, not implementation
  tasks, until Kv responds** — task-runner's job for 7 and 8 is to implement *if and only if* Kv's
  answer requires a code change; if Kv confirms the existing cycle-1 behavior, the task's output is
  an updated `memory/decisions.md` entry marking the decision confirmed, not new code. Item 6 is
  purely content-blocked (the swappable-data structure already exists from T5) — there is no
  design work left, only waiting on the actual brief text.
- **Coding standards, folder structure, MVVM layering, `ApinCore` UI-import restriction, testing
  strategy (AI response content excluded from automated tests, error/refusal paths mocked), and
  commit conventions are unchanged from cycle 1** — see `memory/coding-standards.md`, which is the
  standing convention for this and every future cycle unless explicitly amended there.

## Risks

- **Hardware/account unavailability may block items 4, 5, and 10 for the entire cycle**, exactly
  as it did in cycle 1. Mitigation: sequence these last within their tier so their blockage doesn't
  stall the debt fixes and decision-confirmation items that don't need hardware; treat a
  documented "still blocked" outcome as acceptable per the Definition of Done, not a cycle failure.
- **Items 6, 7, 8 depend on Kv actually responding** during the cycle, not just being asked once.
  Mitigation: surface these as blocking open questions immediately (see below) rather than letting
  implementation silently proceed on cycle-1's assumptions a second cycle running — if no response
  arrives, the plan's fallback is to leave cycle-1's implemented defaults in place and re-flag them
  as still-open in `memory/decisions.md`, exactly as before, rather than guessing a change.
- **The debug capability override (item 3) is a testing aid with a real shipping risk if the
  `#if DEBUG` gate is implemented incorrectly** — a mis-gated override that leaked into a Release
  build would be a security/product-quality regression (someone could force a fake "unsupported"
  or "available" state). Mitigation: this is called out explicitly as its own Definition of Done
  checklist item, not left to be caught incidentally by `/review`.
- **Duplicate-`id` handling (item 1) has no reproducible failure case today** — no current code
  path produces a duplicate `id` — so the fix is defensive/preventive, not a reproduction-driven
  bugfix. Risk: without a real duplicate to test against, unit tests will have to construct the
  duplicate scenario synthetically (e.g. two `JournalEntry` instances with the same `id` inserted
  directly via the test `ModelContainer`); task-runner should do this rather than treating "no
  repro" as "nothing to test."
- **Re-spot-checking spec open question #1 (item 9) could, in principle, surface a changed Apple
  minimum requirement**, which would ripple into `project.yml`'s deployment target and
  potentially invalidate assumptions baked into cycle 1's shipped code. Low probability (already
  verified once, short time since cycle 1) but non-zero; if it does surface a change, treat it as
  a new, separate follow-up item rather than silently patching deployment targets mid-cycle.
- **T15's inline-answer spike (item 10) may again conclude "no-go"** on latency grounds, same as a
  plausible cycle-1 outcome had it been attempted — this remains an acceptable outcome per the
  original plan's risk framing, not a failure, and T13's deep-link baseline (already shipped)
  covers Req 5 regardless.
