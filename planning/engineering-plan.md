# Engineering Plan — Apin v1 (offline personality assistant + studying journal)

Generated by `/plan` (the `planner` subagent) from `planning/spec.md`. `memory/decisions.md`,
`memory/technical-debt.md`, `memory/coding-standards.md`, `memory/apis.md`, and
`memory/database-schema.md` are empty templates (first cycle) — nothing to carry over.

This is the input to `/tasks`, which turns it into `tasks/task-graph.md`.

## How to read this plan

The spec (`planning/spec.md`) leaves five things open (minimum device/OS, personality brief,
exact Spotlight behavior, retention policy, answer language). Blocking the whole plan on those
isn't warranted — each is resolved below with an explicit, stated default assumption so work can
start. Every assumption is repeated in **Risks / Open Questions** at the end so it's visible and
easy for Kv to override before or during implementation. Backlog items that are most exposed to
a given assumption say so in their row.

## Architecture decisions

- **Native SwiftUI app, iOS-only, single Xcode project with a widget extension target and a
  shared local Swift package/framework** (`ApinCore`) for the AI wrapper, persistence models,
  and App Intents — rationale: spec mandates Swift/SwiftUI and on-device Foundation Models; a
  shared package lets the app target, widget extension, and App Intents extension all reuse the
  same journal/model code without duplicating it per target.
- **Assumed minimum platform: iOS 26+, Apple Intelligence–capable hardware (A17 Pro / M-series
  or later, e.g. iPhone 15 Pro and newer)** — rationale: the `FoundationModels` framework
  (`import FoundationModels`, `SystemLanguageModel`, `LanguageModelSession`) that gives on-device
  LLM access to third-party apps was introduced alongside iOS 26 and is gated behind the same
  hardware/region/Apple-Intelligence-enabled requirements as other Apple Intelligence features.
  **This is an assumption, not a verified fact for the day of implementation** — Apple's minimum
  requirements table should be re-checked against current developer docs before task 1/2 are
  implemented, since Apple has moved this bar before. Flagged in Risks.
- **Capability gate is a first-class, testable service (task 2), not a scattered set of
  `if #available` checks** — rationale: requirement 7 is a Must; centralizing the check (OS
  version, hardware capability via `SystemLanguageModel.availability`, Apple Intelligence toggle
  state) into one typed result (`available` / `unsupportedDevice` / `unsupportedOS` /
  `appleIntelligenceDisabled`) lets every entry point (Ask screen, widget, App Intent) render the
  right message instead of guessing.
- **Personality is implemented as a single system-instruction template, not per-call prose** —
  rationale: requirement 2 demands a *consistent* voice; centralizing name/tone/guardrails in one
  builder (task 5) means the tone can be tuned once and every call site (Ask screen, Spotlight
  intent, widget quick-ask) stays in sync.
- **Assumed personality brief (placeholder pending Kv's real brief): "Apin" is a warm, curious,
  encouraging study-buddy voice — concise, plain-language explanations, occasional light
  enthusiasm, never condescending, admits uncertainty rather than fabricating.** This is
  deliberately generic so it's easy to replace; the prompt builder (task 5) should keep the
  brief as isolated, swappable data (not hardcoded across call sites) so refining it later is a
  content change, not a code change. Flagged in Risks.
- **Assumed answer language: mirror the language of the question (English or Indonesian
  supported), defaulting to English when detection is ambiguous** — rationale: Kv is
  Indonesia-based and the spec explicitly raises this as open; mirroring input language is the
  least-surprising default for a personal assistant and Apple's on-device model has multilingual
  capability, but **language support depends on the device's Apple Intelligence language
  settings at runtime and needs verification during task 4/5 implementation.** Flagged in Risks.
- **Journal storage: SwiftData as the source of truth, mirrored to Markdown + JSON files for
  portability (requirement 8), with SwiftData's CloudKit integration for sync (requirement 9)**
  — rationale: SwiftData is the native, SwiftUI-integrated persistence layer with predicate-based
  search (requirement 4) and a built-in CloudKit sync path, avoiding hand-rolled sync code;
  writing a parallel Markdown/JSON mirror on every save (task 12) satisfies "portable, not locked
  to this app" without waiting on a full export/import UI, and gives the future Mac companion a
  plain-file interface instead of requiring it to link SwiftData/CloudKit.
- **Assumed retention policy: entries are kept forever by default, no automatic archiving or
  deletion** — rationale: "journal" implies a durable record; spec doesn't ask for retention
  limits and nothing in the use cases implies pruning. Manual delete (single entry) is in scope
  as a baseline data-hygiene affordance even though not explicitly listed as a requirement, since
  its absence would make user testing during development unnecessarily awkward. Flagged in Risks
  as an assumption Kv should confirm.
- **Assumed Spotlight behavior: deep-link App Intent (task 13) + indexed journal entries (task
  14) are the committed baseline; a fully inline Siri/Spotlight-answered App Intent (task 15) is
  a Should-priority spike, not a guarantee** — rationale: App Intents surfaced through
  Siri/Spotlight are subject to Apple's execution time budget, and on-device LLM inference
  latency is variable and not fully within app control; committing to inline answers before
  confirming the latency fits the budget risks a Must-have requirement slipping on external
  constraints. Deep-link (open app, prefill query, produce the answer inside the app UI) always
  satisfies requirement 5's "let the user ask a question or jump into the app," so it's the safe
  floor; inline is upside if the spike (task 15) succeeds.
- **App Intents and widget code live in the shared `ApinCore` package, not duplicated per
  extension target** — rationale: both the widget's quick-ask button and the Spotlight
  `AskApinIntent` need to trigger the same "capture question → run model → save to journal" flow;
  one implementation avoids the two entry points drifting.
- **MVVM within each feature module** (`Ask`, `Journal`, `Widgets`, `AppIntents`), with `Core/AI`
  (Foundation Models wrapper + personality builder) and `Core/Persistence` (SwiftData models +
  repository) as dependency-free-of-UI layers — rationale: keeps the non-deterministic AI layer
  and the persistence layer independently unit-testable without pulling in SwiftUI.
- **Testing strategy**: unit tests (XCTest) for everything deterministic — capability gate logic,
  journal repository CRUD/search/predicates, personality prompt construction (structure, not
  wording), export file writer, streak/date-grouping logic. AI *response content* is explicitly
  not unit-tested (non-deterministic on-device generation); instead, model integration is
  smoke-tested manually per task and the wrapper's error-handling paths (timeout, unavailable,
  refusal) are unit-tested with a fake/mock session. XCUITest is optional/deferred — solo dev, no
  deadline, so manual QA pass per `/qa` is the primary UI safety net for v1.
- **SwiftLint** as the style/lint tool, run locally (no CI configured this cycle — no backend,
  solo dev; CI is out of scope until there's a second contributor or release pipeline need).

### Coding standards proposal (initial defaults — promoted to `memory/coding-standards.md` by `/remember`, not edited here)

- **Naming**: Swift API Design Guidelines — `UpperCamelCase` for types/protocols, `lowerCamelCase`
  for properties/functions/enum cases. One primary type per file, filename matches the type
  (`JournalEntry.swift`, `AskApinIntent.swift`). View models suffixed `ViewModel`
  (`AskViewModel`), SwiftData models suffixed nothing extra (`JournalEntry`, not `JournalEntryModel`).
  Protocols describing capability end in `-ing`/`-able` where natural (`ModelSessionProviding`);
  otherwise a plain noun.
- **Structure**: folder-by-feature at the app-target level (`Features/Ask`, `Features/Journal`,
  `Features/Widgets`), shared non-UI code in the `ApinCore` package under `Sources/AI`,
  `Sources/Persistence`, `Sources/AppIntents`. UI layers may depend on `ApinCore`; `ApinCore` may
  never import SwiftUI/UIKit — keeps the AI/persistence layer reusable from the widget and App
  Intents extensions without pulling in app-target UI code.
- **Style**: SwiftLint with Swift's default rule set plus `line_length: 120` (warning), trailing
  closures preferred, `async/await` preferred over completion-handler APIs for all new code,
  `// MARK: -` section markers in files over ~150 lines.
- **Testing**: new logic in `Core/AI` and `Core/Persistence` requires unit tests in the same PR;
  test files mirror source path under `Tests/` with a `Tests` suffix
  (`JournalRepositoryTests.swift`). SwiftUI views are not required to have tests unless they
  contain non-trivial logic (e.g. a view model). AI response *content* is out of scope for
  automated tests per the testing strategy above.
- **Commits**: Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`),
  imperative mood subject line, task ID referenced in the body when the commit closes a
  `tasks/task-graph.md` item (e.g. `Refs: T-006`). Branch naming `feature/<short-desc>` or
  `fix/<short-desc>`.

## Constraints

- Requires Apple Intelligence–capable hardware and an iOS version supporting the
  `FoundationModels` framework — exact minimum is an assumption (iOS 26+, A17 Pro/M-series+) that
  must be reverified against current Apple developer docs before/at task 1–2 implementation, since
  Apple has adjusted these bars before and may again.
- Solo developer, no backend/server — everything must work standalone on-device; iCloud sync
  (requirement 9) uses Apple's CloudKit infrastructure only, no custom server.
- Swift/SwiftUI native iOS app; no cross-platform framework.
- No specific deadline — sequencing favors correctness and small reviewable increments over
  speed.
- No prior `memory/` decisions, tech debt, coding standards, APIs, or schema to reconcile with —
  this plan establishes the initial baseline for all of them.

## Definition of Done

- [ ] Meets the requirement(s) it maps to
- [ ] Passes existing tests; new tests added for new deterministic behavior (per testing strategy
      above — AI response wording is exempt)
- [ ] Follows the coding standards proposed above (pending promotion to
      `memory/coding-standards.md`)
- [ ] No new entries in `memory/technical-debt.md` without sign-off
- [ ] Verified to make no network requests when producing an answer (requirement 1 is
      safety-critical to the product's value proposition — spot-check with network conditioning
      / Instruments during `/qa` for any task touching the Ask flow)
- [ ] Unsupported-device/OS path manually verified not to crash or silently no-op (requirement 7)
- [ ] Reviewed via `/review` and validated via `/qa`

## Risks

- **Minimum device/OS assumption may be wrong or may change.** Mitigation: task 2 (capability
  gate) isolates the version/hardware check behind one service so a corrected minimum is a
  small, localized change; verify against current Apple docs before starting task 1.
- **Personality brief is a placeholder, not Kv's real intent.** Mitigation: task 5 keeps the
  brief as isolated, swappable data rather than scattering tone instructions across call sites,
  so revising it later doesn't touch multiple files; get Kv's actual brief before or during
  sprint 1 to avoid throwaway prompt-tuning work.
- **Answer-language default (mirror input, English fallback) is unconfirmed and depends on
  on-device model language support at runtime**, which needs hands-on verification once
  Foundation Models access is available in the dev environment — may not actually support
  Indonesian on-device; if not, requirement scope needs to shrink to English-only and that should
  be surfaced back to Kv rather than silently degraded.
- **Inline Spotlight/Siri answers (task 15) may not be feasible** if on-device inference latency
  exceeds Apple's App Intent execution time budget — mitigated by treating it as a Should-priority
  spike with a defined fallback (deep-link only, task 13) that still satisfies requirement 5.
- **On-device model output is non-deterministic and subject to Apple's built-in safety
  guardrails/refusals**, which can surface as an oddly-toned or declined answer that breaks
  personality consistency (requirement 2) in ways unit tests can't catch. Mitigation: wrapper
  error/refusal handling is unit-tested for graceful degradation (task 4); actual tone quality is
  a manual `/qa` concern, not an automated one.
- **CloudKit sync (task 17) is a Should, not a Must, and has real complexity** (conflict
  resolution, first-sync backfill, schema evolution). Mitigation: sequenced after local-only
  journal (task 6) and portable export (task 12) both work standalone, so sync can slip a sprint
  without blocking the Must-have requirements.
- **Retention policy assumption (keep forever, no auto-archive)** could be wrong if Kv wants
  pruning or an archive view later — low cost to change since no requirement or task currently
  depends on data being finite/expiring.
- **Portable export format (task 12) has no consumer yet** (Mac companion is out of scope this
  cycle) — risk of over- or under-engineering the export shape without real feedback. Mitigation:
  keep the Markdown/JSON schema simple and versioned (a `schemaVersion` field) so it can evolve
  when the Mac companion cycle actually starts.
- **Testing AI-generated content is inherently limited** — the plan accepts manual `/qa` as the
  safety net for response quality/tone rather than pretending automated tests can cover it;
  documented explicitly so `/review` and `/qa` don't flag its absence as an oversight.
