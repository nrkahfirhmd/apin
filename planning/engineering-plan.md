## Architecture decisions

No new architecture this cycle. SwiftData + `ApinCore` local package + App Group
(`group.com.apin.app`) + CloudKit (`ModelConfiguration(cloudKitDatabase: .automatic)`), as
established in cycle 1 and re-affirmed in cycle 2 (see `memory/database-schema.md`,
`memory/adrs/001-*`, `memory/adrs/002-*`, `memory/adrs/003-*`), remain the baseline and are not
being revisited. The decisions this cycle adds are narrow:

- **Personality brief is a content-only change, no design work** — `PersonalityBrief.swift`
  already exists as isolated, swappable data specifically so this would be a content change, not
  a code change (cycle 1's T5 built it this way for exactly this purpose; cycle 2's T6 confirmed
  no design work remains). This cycle's task-runner must not restructure
  `PersonalitySystemInstructionBuilder.swift`'s building logic or the shape of
  `PersonalityBrief.swift`'s type — only its content (name-origin framing, tone descriptors,
  character-voice guidance derived from the Crow Armbrust reference: witty, charming,
  mercenary-rogue energy, quips rather than lectures, cocky but likable). Existing structural
  tests in `PersonalitySystemInstructionBuilderTests.swift` must keep passing unmodified in
  shape, per `memory/coding-standards.md`'s testing strategy (AI response content stays out of
  automated assertions).
- **Human-in-the-loop tasks produce a script, not a verified result** — items 2–4 exist because
  this session (and, per `memory/decisions.md`, likely any orchestrating CLI session) has no
  tooling to interactively drive a physical device's UI: Instruments capture, typing real
  Indonesian questions, and timing a live response are all real-time human-device interactions,
  not something a task-runner subagent can perform itself. Each of these three tasks' concrete
  deliverable is a precise, self-contained manual test script — exact steps, exact things to
  observe/measure, exact pass/fail criteria — plus a designated place to record Kv's result (a
  new file per script under `review/manual-verification/`, e.g.
  `review/manual-verification/zero-network-check.md`,
  `review/manual-verification/indonesian-fluency-check.md`,
  `review/manual-verification/siri-spotlight-latency-spike.md`, each with a "Result" section left
  blank for Kv to fill in). A task is **done** when the script exists, is precise enough to
  execute without further clarification, and has been handed to Kv — not when the underlying
  technical-debt item is actually resolved. Closing out the technical-debt item happens in item
  5, contingent on Kv's report, and may legitimately slip past this cycle's boundary if Kv hasn't
  executed the scripts yet by the time `/qa` runs — that is an acceptable, explicitly-tracked
  outcome per this same framing cycle 2 used for hardware-availability blockage, not a planning
  failure.
- **Retention policy and T13 auto-submit UX: no code change, decisions-log entries only** — both
  are confirmed-as-shipped by Kv this session. Nothing in `SwiftDataJournalRepository.swift` or
  the T13 deep-link call site needs to change. Writing the confirming `memory/decisions.md`
  entries is `/remember`'s job once this cycle's implementation completes, not a task-runner
  deliverable — there is no backlog item for either.
- **Coding standards, folder structure, MVVM layering, `ApinCore`'s UI-import restriction, and
  testing strategy are unchanged from cycles 1–2** — see `memory/coding-standards.md`, the
  standing convention for this and every future cycle unless explicitly amended there.

## Constraints

- Solo developer (Kv), no backend/server component, no deadline — everything must remain
  standalone on-device; CloudKit sync uses Apple's infrastructure only.
- On-device only, no cloud/hybrid model fallback (spec non-goal, unchanged).
- Swift/SwiftUI native iOS app; no cross-platform framework; no new targets/extensions needed
  this cycle — item 1 lives entirely in `ApinCore/Sources/AI/PersonalityBrief.swift`; items 2–4
  produce new Markdown files under `review/manual-verification/`, not app code.
- `memory/coding-standards.md` (naming, structure, style, testing, commits) governs all new work
  this cycle, including item 1's content change and item 5's contingent updates.
- No new architecture is warranted or in scope this cycle — the personality-brief swap and the
  three verification checklists are explicitly content/documentation tasks per their own scoping
  above, not implementation tasks that could plausibly need new structure.
- **Working-tree hygiene**: at the time this plan was written, `git status` shows uncommitted
  changes to `Apin.xcodeproj/project.pbxproj`, `Apin/Apin.entitlements`, `Apin/ApinApp.swift`,
  `ApinTests/ApinAppModelConfigurationTests.swift`, `ApinWidget/ApinWidget.entitlements`,
  `ApinWidget/JournalWidgetStore.swift`, and `ApinWidgetTests/JournalWidgetStoreTests.swift` —
  content consistent with cycle 2's already-`resolved` App Group identifier fix
  (`memory/technical-debt.md`'s "App Group / iCloud container identifier drift" entry), just not
  yet committed. This plan does not add a backlog item for committing it (it's leftover cycle-2

## Risks

- **Items 2–4 may sit unexecuted past this cycle's boundary** if Kv doesn't get to the physical
  device before `/qa` runs — this is explicitly modeled as acceptable (item 5 is a contingent
  follow-up, not a hard blocker on cycle 3's closure) but it does mean the three long-standing
  technical-debt/decision items (zero-network verification, Indonesian fluency, latency spike)
  could carry into cycle 4 for a third cycle running. Mitigation: scripts must be precise and
  low-friction enough (exact steps, no ambiguity) that Kv can execute them in a short standalone
  session without needing to re-read this plan or ask clarifying questions first.
- **Item 1's content risk**: translating a character reference (Crow Armbrust) into system-prompt
  guidance risks either being too thin (doesn't actually change the model's voice) or overshooting
  into unwanted behavior (e.g. the model refusing to answer plainly, or becoming flippant on
  serious questions). Mitigation: keep the brief's guidance behavior-anchored (quips over
  lectures, concise, cocky-but-likable, still answers directly) rather than trying to encode
  the character's full backstory/setting — this is a *tone* reference, not a roleplay/persona
  simulation, and `memory/coding-standards.md`'s testing strategy already excludes AI response
  wording from automated tests, so this can only be sanity-checked by reading actual model output
  manually during implementation, not asserted in a unit test.
- **Uncommitted cycle-2 diff sitting in the working tree** (see Constraints) could get tangled
  with cycle 3's own commits if not reconciled first — mitigation is procedural (commit or stash
  it explicitly before cycle 3's first task lands), not a design change.
- **Retention policy and T13 auto-submit UX decisions were captured only in this session's chat**,
  not yet written to `memory/decisions.md` — until `/remember` runs, a future session reading only
  the repo (not this conversation) would still see them as open in `memory/decisions.md`'s existing
  entries. Low risk since this plan itself records the resolution and `/remember` is a mandatory
  phase of this project's loop, but worth flagging so `/tasks`/`/implement` doesn't reopen them as
  if unresolved.
