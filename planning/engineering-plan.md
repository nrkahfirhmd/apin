# Engineering Plan — Apin v1.4 (Cycle 5: design-handoff foundation + Ask/Journal recreation)

Generated by `/plan` (the `planner` subagent) from `planning/spec.md` (unchanged since cycle 1),
`memory/` (decisions, technical-debt, coding-standards, apis, database-schema, ADRs), and — new
this cycle — `design_handoff_apin/README.md` and `design_handoff_apin/apin-green.css`, a
high-fidelity UI/UX handoff for two screens (Ask + answer, Journal) that landed after cycle 4
closed. This overwrites cycle 4's `planning/engineering-plan.md` and is the input to `/tasks`,
which will regenerate `tasks/task-graph.md`.

## How to read this plan

Cycles 2-4 were small (1-5 items), driven by memory/technical-debt follow-up. This cycle is
different in kind: `design_handoff_apin/README.md` is explicit that it is "high fidelity" —
"[c]olors, type, spacing, radii, and copy are final" and the task is to "recreate these designs
… pixel-accurately," with a real (not cosmetic) interaction-model change ("[t]he interaction
model (typing, answer delay, Apin's follow-up chips, auto-filing) is real and functional in the
prototype — mirror the behavior"). Verifying the current codebase against that bar surfaced four
separate categories of work, not one:

1. **A design-token/theming foundation that does not exist yet.** `grep -rn
   "oklch|Theme|DesignToken|ColorPalette|Phosphor|Generable"` across `Apin/` and `ApinCore/`
   returns zero hits (confirmed directly this session); no `.ttf`/`.otf` font file exists anywhere
   in the repo (confirmed via `Glob`). Nothing to extend — this is a from-scratch task.
2. **A structured-output architecture change to the AI layer.** The handoff's "Apin's follow-up"
   block (a follow-up question + tappable chips, `askBack`-toggleable) and per-answer topic-tag
   pills have no backing implementation. `ApinCore/Sources/AI/AssistantSessionService.swift`'s
   entire public surface is two plain-`String` methods — `send(prompt:) async ->
   Result<String, AssistantResponseError>` (line 57) and `streamResponse(prompt:) ->
   AsyncThrowingStream<String, Error>` (lines 77-92) — mirrored exactly by
   `Apin/Features/Ask/AssistantSessionProviding.swift` (lines 20-28, "mirrors
   `AssistantSessionService`'s … API exactly"). There is no concept anywhere of a model call
   producing more than an answer string.
3. **Two screens' worth of pixel-accurate visual recreation**, including one genuine behavioral
   gap, not just styling: `AskViewModel.swift`'s `AskPhase` enum (lines 33-44) tracks exactly one
   in-flight/most-recent exchange (`.idle/.loading/.streaming/.answered/.failed`) — there is no
   running list of Q&A pairs for the current app session. The handoff's own state table
   (`design_handoff_apin/README.md`, "State management") defines `messages: [Message]` as an
   array accumulated across the session, rendered as a scrolling stack of question/answer blocks.
   Recreating the Ask screen's look without also introducing that message-history state would
   misrepresent the design, not just under-style it.
4. **Root navigation composition.** `Apin/ContentView.swift` (lines 17-23) still renders only
   `AskView` — its own header comment calls this "T1's placeholder … NOT a final root-navigation
   composition combining Ask + Journal." `JournalListView.swift`'s header (lines 37-39) says the
   same thing from the other side ("no root navigation composition exists yet (ContentView is
   still T1's placeholder)"). The handoff's Ask header has a journal button with a **live entry
   count** that navigates to Journal — this requires that composition to exist, not a styling
   change to `ContentView`.

**Sizing call, surfaced explicitly rather than hidden in the backlog:** items 1, 2, and 4 above are
foundational — the pixel-accurate screen work in item 3 cannot be done well without a token layer
to draw from and a settled shape for what a model call returns. This plan therefore splits the
backlog into **Stage A (foundation)** and **Stage B (screen recreation)**, in that order.

**Resolved 2026-08-12 (see `memory/decisions.md`):** Kv confirmed **Stage A only for Cycle 5**.
Stage B (backlog items 8-11) is deferred to a follow-up cycle, to be planned fresh once Stage A
has landed and been reviewed — `/tasks` should generate a task graph covering Stage A (items 1-7)
plus item 12 (carried-forward Spotlight recheck) only. Stage B's table below is retained in this
document as the scoped-but-deferred plan for that follow-up cycle, not as this cycle's committed
work.

One item is carried forward, not dropped, despite the cycle's focus shifting: cycle 4's T4 (record
Kv's execution of the Siri/Spotlight invocation re-check script) is still `blocked` per
`tasks/task-graph.md`'s "Blocked / notes" section, and `memory/decisions.md` has no newer entry
recording Kv's report. It is backlog item 13 below, unchanged in substance, carried forward at
low priority relative to this cycle's design-handoff focus. Everything else cycle 4 touched

## Architecture decisions

- **Token layer lives in the `Apin` app target, not `ApinCore`, and is a new architectural surface, not an extension of an existing one.** `ApinCore`'s zero-SwiftUI/UIKit-import rule (`memory/coding-standards.md`, `JournalEntry.swift` line 23) is absolute and unrevisited by this plan — colors/fonts/spacing constants that are inherently SwiftUI/UIKit types cannot live there. Where the token layer sits relative to `Features/*` (a new `Apin/DesignSystem/` folder vs. elsewhere) is left to `/tasks` to place per `memory/coding-standards.md`'s "folder-by-feature" convention, extended with a new non-feature folder for cross-cutting UI, mirroring how `Apin/Common` already exists for `StatusMessageView`.
- **OKLCH colors are pre-converted to device-color-space component values at token-definition time, not computed at runtime.** No SwiftUI/UIKit OKLCH initializer is known to exist as of iOS 26 (this session's knowledge, not a live-doc-verified fact this cycle — flagged as a verification step for whichever task implements item 1, same rigor the routine iOS-floor checks in prior cycles used for other framework facts). Each converted color constant should retain the source `oklch(...)` string as an adjacent comment so a future re-tune of `apin-green.css` (its own header says "retune it here") can be re-derived rather than reverse-engineered from an sRGB value.
- **Font: SF Pro (system), not bundled Inter.** The handoff explicitly sanctions this substitution ("substitute SF Pro if Inter isn't bundled, but keep the weights and sizes") and no font asset exists in the repo today — bundling Inter is unforced overhead the handoff itself waives.
- **Icons: SF Symbol equivalents, not the Phosphor SwiftUI package.** The handoff explicitly allows either option. This project has never taken on an external SPM dependency (`project.yml`'s only `packages:` entry is the local `ApinCore`, lines 17-19) — three icons is not a strong enough case to be the first. If a future cycle needs a much larger Phosphor icon surface, this decision should be revisited explicitly, not silently overridden.
- **Structured model output via Foundation Models guided generation (`@Generable`), one call producing `{answer, followUpQuestion, chips, tags}`, over either a second model call or text-convention parsing.** Rationale: a single call is cheaper (latency/battery, consistent with the product's fully-offline, on-device value proposition) and native framework support is more robust against model-output drift than parsing a delimited string convention. **This is a genuine architectural change to `ApinCore/Sources/AI/AssistantSessionService.swift`'s public surface** (both `send`/`streamResponse` currently return plain `String`/`AsyncThrowingStream<String, Error>`) and to `Apin/Features/Ask/AssistantSessionProviding.swift`, which mirrors it exactly by design (its own header: "mirrors `AssistantSessionService`'s … API exactly"). Whether Foundation Models' streaming path supports incremental partial-`@Generable` snapshots (needed for the handoff's "stream token-by-token … keep the three-dot indicator until first token" requirement to apply to a *structured* response, not just a string) has **not been live-verified this session** — flagged explicitly as a first-implementation-step verification for whichever task takes this on, not assumed. If partial-structured streaming turns out unsupported on the current SDK, the fallback is two calls (stream the answer text as today, then a second short structured call for `followUpQuestion`/`chips`/`tags` once the answer completes) — worth deciding then, not guessed at now.
- **No `JournalEntry` schema/migration change.** Verified directly against the handoff's own state table: `tags: [String]` already exists (`JournalEntry.swift` line 40); `excerpt` is derived at render/query time (not stored — see backlog item 5); `followUpQuestion`/`chips` are ephemeral, Ask-session-only `Message` state per the handoff's own type distinction, never part of a persisted `JournalEntry`. This avoids `memory/database-schema.md`'s documented CloudKit-mirroring migration constraints (inline defaults, no unique-constraint support) entirely for this cycle.
- **Auto-generated tags seed, not replace, manual tag editing.** `JournalEntryDetailView`'s existing T11 manual add/edit UI stays; item 4's structured call's `tags` output becomes the initial value passed to `JournalEntry.save(...)`, same as any other initial value. No `JournalRepository`/`JournalQuery` interface change needed — both already operate on plain `[String]`.
- **Ask-session message-history state is new, not a reinterpretation of `AskPhase`.** `AskPhase` (`AskViewModel.swift` lines 33-44) remains the state machine for a *single* in-flight exchange (idle/loading/streaming/answered/failed); a new, separate `messages`-shaped array is additive on top of it for the running session view, per the handoff's own distinct `messages`/no-phase-equivalent state shape. `/tasks` should treat this as new state, not a rename/reshape of the existing enum, to avoid breaking `AskViewModelTests`' existing phase-transition coverage.
- **Root navigation composition owns reconciling `WeeklyDigestView`'s and `AskDeepLinkCoordinator`'s existing entry points**, not a separate task — both already exist and work (cycle 1-2 T12/T13); the recreation must carry them forward into whatever the new Ask ↔ Journal composition looks like, not drop them as a side effect of a visual rewrite.

## Risks

- **Scope risk (the sizing call this plan is explicitly surfacing, not hiding):** Stage A alone
  touches the AI layer's public contract (item 4), the persistence layer's save path (items 5-6),
  and root navigation (item 7) — before any screen actually looks like the handoff. Attempting
  Stage A + Stage B in a single `/tasks` → `/implement` pass is a materially larger, more
  interdependent scope than any prior cycle. Mitigation: this plan recommends Stage A as this
  cycle's committed scope and Stage B as a follow-up-cycle candidate (see Open Questions) — but
  the final call is Kv's, made before `/tasks` runs, not assumed by this plan.
- **Structured-generation streaming is an unverified assumption.** Item 4's Architecture Decision
  section already flags this: whether Foundation Models supports incremental partial-`@Generable`
  streaming (vs. only a single non-streamed structured response) has not been checked against
  current Apple documentation this session. If unsupported, the fallback (stream the answer text
  as today, structured call afterward) changes the UX slightly (chips/tags appear after the answer
  finishes, not alongside it) — worth flagging to Kv now rather than discovering it mid-implementation
  with no fallback already decided.
- **OKLCH → sRGB/P3 conversion accuracy.** Hand- or tool-converted values may not visually match
  the CSS reference exactly across color spaces/displays; "pixel-accurate" should be read as
  "accurate within normal cross-color-space rendering tolerance," not byte-identical. Mitigation:
  keep source `oklch(...)` strings alongside every converted constant so discrepancies are
  correctable later without re-deriving from scratch.
- **Two overlapping "weekly activity" surfaces.** The existing `WeeklyDigestView` (streak + count,
  cycle 2's T12) and the handoff's new Journal week-strip (a 7-bar activity chart in the Journal
  header) are not the same feature but do overlap in intent. **Resolved 2026-08-12** (see Open
  Questions #2, `memory/decisions.md`): Kv placed the digest entry point in the recreated Journal
  header, alongside the week strip — not merged into one feature, but co-located by product call.
- **`AskPhase` and the new message-history state must not silently merge into one enum** during
  implementation convenience — doing so would risk breaking `AskViewModelTests`' existing
  phase-transition coverage and blur a state machine (single exchange) with a session log
  (multiple exchanges) that the handoff itself keeps conceptually separate (`typing: Bool` gates
  the indicator; `messages: [Message]` is the accumulated log).
