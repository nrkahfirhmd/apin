## Architecture decisions

No new architecture this cycle. SwiftData + `ApinCore` local package + App Group
(`group.com.apin.app`) + CloudKit (`ModelConfiguration(cloudKitDatabase: .automatic)`), as
established in cycle 1 and re-affirmed in cycles 2-3 (see `memory/database-schema.md`,
`memory/adrs/001-*`, `memory/adrs/002-*`, `memory/adrs/003-*`), remain the baseline and are not
being revisited. The decisions this cycle adds are narrow:

- **Item 1 is a content-only change, gated on an explicit product decision, not an implementation
  detail** — there is no separate language-detection code path to remove: `languagePolicy` is a
  single `String` field on `PersonalityBrief`, composed verbatim into the system instruction by
  `PersonalitySystemInstructionBuilder.build(from:)` (`sections.append("Language handling:
  \(brief.languagePolicy)")`). Shrinking to English-only is therefore a one-field content edit,
  not a refactor. `PersonalitySystemInstructionBuilderTests.swift`'s structural assertion
  (`instructions.contains(PersonalityBrief.placeholder.languagePolicy)`) reads the property
  dynamically rather than asserting a hardcoded string, so it will keep passing regardless of the
  new wording — verified by reading the test directly during planning, not assumed. What this
  plan does **not** do is treat the strong signal (0/5 technical fail + Kv's stated "only English
  is enough" read) as itself sufficient authorization to implement — per this project's
  established pattern (personality brief, retention, T13 auto-submit all required an explicit,
  session-recorded Kv confirmation before a backlog item was scoped as actionable), item 1 stays
  gated until Kv confirms in this planning session. See Open Questions.
- **Items 2 and 3 are complementary, not sequential** — item 2 (build/metadata audit) and item 3
  (device re-check, voice + Settings toggles) investigate independent hypotheses for the same
  symptom and can run in parallel; `/tasks` should not impose an artificial dependency between
  them. Item 3's script should reference item 2's findings where useful (e.g., "here's what the
  build-level check found; does that match what you observe") but does not need item 2 to complete
  first to be executable.
- **Item 3 stays a script deliverable, not a verified outcome, for the same reason Cycle 3's T2-T4
  did** — this session still has no tooling to interactively drive a physical device's Siri/UI
  (voice invocation, Settings navigation, real-time observation). A task is **done** when the
  script exists, is precise enough to execute without further clarification, and has been handed
  to Kv — not when the underlying gap is actually diagnosed or fixed. Closing it out is item 4,
  contingent on Kv's report, and may legitimately slip past this cycle's boundary, same as prior
  cycles' device-verification items.
- **Coding standards, folder structure, MVVM layering, `ApinCore`'s UI-import restriction, and
  testing strategy are unchanged from cycles 1-3** — see `memory/coding-standards.md`, standing
  convention for this and every future cycle unless explicitly amended there.

## Constraints

- Solo developer (Kv), no backend/server component, no deadline — everything must remain
  standalone on-device; CloudKit sync uses Apple's infrastructure only.
- On-device only, no cloud/hybrid model fallback (spec non-goal, unchanged).
- Swift/SwiftUI native iOS app; no cross-platform framework; no new targets/extensions needed this
  cycle — item 1 lives entirely in `ApinCore/Sources/AI/PersonalityBrief.swift`; item 2 produces
  findings recorded in its task's completion notes (and, if anything is actually wrong, a follow-up
  backlog candidate for a future cycle — item 2 itself is diagnostic, not a fix); item 3 produces a
  new Markdown file under `review/manual-verification/`, not app code.
- `memory/coding-standards.md` (naming, structure, style, testing, commits) governs all new work
  this cycle.
- No new architecture is warranted or in scope this cycle.
- **Item 1's sign-off was recorded 2026-08-11** — Kv explicitly confirmed "yes, English-only" in
  this planning session (see `memory/decisions.md`). Item 1 is ungated and actionable by `/tasks`.
- Item 2's build/metadata audit should be run against the current toolchain/SDK (not assumed
  identical to Cycle 1's T13 finding) — Apple's `appintentsmetadataprocessor`/
  `appintentsnltrainingprocessor` behavior is SDK-version-dependent per ADR 001's own "Consequences"
  section, and should be re-verified rather than assumed stable.

## Risks

- **Item 1 could get implemented prematurely if `/tasks`/`/implement` treats this plan's existence
  as sufficient authorization.** The signal is strong (0/5 technical fail plus Kv's own stated
  read), but per this project's own established pattern, strong signal is not the same as an
  explicit sign-off recorded in the planning session. Mitigation: item 1 is explicitly marked
  gated in the backlog table, Architecture decisions, and Constraints sections, and `/tasks` should
  encode that precondition directly into the task rather than relying on this plan being reread at
  implementation time.
- **Item 2's audit may not find anything static/wrong** (ADR 001's Cycle-1 verification passed at
  the time), in which case the Spotlight-invocation gap may be a runtime/device-state issue (stale
  Siri/Spotlight index cache, a Settings toggle, or something else not visible from the build
  artifacts) rather than a code defect — this is a legitimate, useful negative result, not a task
  failure, and narrows item 3's investigation rather than replacing it.
- **Item 3 may sit unexecuted past this cycle's boundary**, same risk class as Cycle 3's T2-T4 —
  mitigated the same way (a precise, low-friction, self-contained script Kv can run without
  re-reading this plan). If this recurs again next cycle, it's worth Kv considering (as Cycle 3's
  plan already flagged) whether device-verification items should move to a standing,
  cycle-independent checklist rather than re-entering the sprint-planning loop each time.
- **If item 1 ships English-only before item 3 resolves the Spotlight-invocation gap**, and it
  later turns out invocation was silently degraded by something language-instruction-adjacent
  (unlikely — the two are unrelated subsystems — but worth naming), the two changes landing in the
  same cycle could make attribution harder if something regresses. Mitigation: items 1 and
  2/3 touch entirely disjoint files (`PersonalityBrief.swift` vs. `AskApinShortcutsProvider.swift`/
  `AskApinIntent.swift`/build tooling) with no shared code path, so this is a low-probability risk
  noted for completeness rather than something requiring sequencing.
