## Task details

### T1 — Project scaffolding
- **Backlog item:** `planning/engineering-plan.md` item #1 (Must)
- **Scope:** Create the Xcode project: `Apin` app target, `ApinWidget` widget extension
  target, and a local Swift package `ApinCore` (added as a local package dependency of both
  targets) with subfolders `Sources/AI`, `Sources/Persistence`, `Sources/AppIntents` (empty
  scaffolds, no logic yet — later tasks fill these in). Add SwiftLint config at repo root.
  Set up folder-by-feature layout in the app target: `Features/Ask`, `Features/Journal`,
  `Features/Widgets`. Set deployment target per the Notes below. Does NOT implement any
  capability-gate, AI, persistence, or UI logic — those are later tasks.
- **Dependencies:** none
- **Acceptance criteria:**
  - Project builds and runs (empty/placeholder screens acceptable) on the app target and the
    widget extension target.
  - `ApinCore` package resolves as a local dependency from both the app target and the
    widget extension target.
  - SwiftLint runs clean (or with only the agreed `line_length: 120` warning tier) against
    the scaffolded files.
  - Folder structure matches the layout above; no logic beyond scaffolding/boilerplate.
- **Notes:**
  - Deployment target: assume iOS 26+, Apple Intelligence–capable hardware (A17 Pro /
    M-series or later). This is an unverified assumption from the plan — re-check against
    current Apple developer documentation as part of this task, since Apple has moved this
    bar before; if the actual minimum differs, use the verified value instead and flag the
    discrepancy in the task's completion notes for `/review`.
  - `ApinCore` must never import SwiftUI/UIKit (keeps it reusable from the widget/App
    Intents extensions without pulling in app-target UI code).
  - SwiftLint rule set: Swift defaults + `line_length: 120` (warning), trailing closures
    preferred, `async/await` preferred over completion handlers, `// MARK: -` section
    markers in files over ~150 lines.
  - Naming: Swift API Design Guidelines — `UpperCamelCase` types/protocols,
    `lowerCamelCase` properties/functions/enum cases, one primary type per file with
    filename matching the type, view models suffixed `ViewModel`.
  - Commits: Conventional Commits (`feat:`, `fix:`, `chore:`, etc.), branch naming
    `feature/<short-desc>` or `fix/<short-desc>`, reference task ID in commit body
    (`Refs: T1`).

### T2 — Capability gate service
- **Backlog item:** item #2 (Must), Req 7
- **Scope:** A typed, testable service in `ApinCore/Sources/AI` that checks OS version,
  hardware capability (`SystemLanguageModel.availability`), and Apple Intelligence toggle
  state, returning one typed result. Does NOT build any UI (that's T3/T7) and does NOT call
  the model (that's T4).
- **Dependencies:** T1
- **Acceptance criteria:**
  - Exposes a typed result with (at minimum) the four cases described in the plan:
    `available`, `unsupportedDevice`, `unsupportedOS`, `appleIntelligenceDisabled`.
  - Unit-tested (XCTest) for each branch using fakes/mocks for OS version and
    `SystemLanguageModel.availability` — no live device dependency required to pass tests.
  - No SwiftUI/UIKit import.
- **Notes:** This is the single source of truth every entry point (Ask screen, widget,
  App Intent) will branch on — do not let callers re-derive availability with their own
  `if #available` checks.

### T3 — Unsupported-device/OS UX screen
- **Backlog item:** item #3 (Must), Req 7
- **Scope:** A SwiftUI screen in the app target that renders a clear, non-crashing,
  non-silent explanation when T2's capability gate returns anything other than `available`,
  distinguishing at least "this device/OS can't run it" from "Apple Intelligence is
  disabled" (the latter is user-fixable via Settings, the former isn't — message
  accordingly). Does NOT implement the Ask screen itself (T7 composes this screen in).
- **Dependencies:** T1, T2
- **Acceptance criteria:**
  - One screen/view per non-`available` capability-gate case, or a single view that
    branches its copy on the case — either is acceptable as long as messaging differs
    meaningfully between "unsupported hardware/OS" and "Apple Intelligence disabled."
  - Manually verified (per plan's Definition of Done) not to crash or silently no-op when
    the capability gate reports each non-available case.
- **Notes:** Feeds directly into T19's polish pass later — keep this visually simple now,
  polish is a separate task.

### T4 — FoundationModels session wrapper
- **Backlog item:** item #4 (Must), Req 1
- **Scope:** A service in `ApinCore/Sources/AI` that creates a `LanguageModelSession`,
  accepts a system-instructions string (from whatever caller — do not hard-import T5's
  concrete builder type, accept a plain `String`/lightweight protocol so this task doesn't
  block on T5), sends a prompt, streams/awaits the response, and maps FoundationModels
  framework errors (timeout, unavailable, refusal, etc.) to app-level typed errors. Does
  NOT build the personality content itself (T5) and does NOT build any UI (T7).
- **Dependencies:** T1
- **Acceptance criteria:**
  - Wrapper's public API supports both a streaming and/or awaited full-response path
    sufficient for T7's loading/streaming UI.
  - Error-handling paths (timeout, unavailable, refusal) are unit-tested with a
    fake/mock session per the plan's testing strategy — model *content* is not tested.
  - Verified (manually, e.g. via network conditioning/Instruments) to make zero network
    requests when producing a response — this is safety-critical per the Definition of Done.
  - No SwiftUI/UIKit import.
- **Notes:** Can be implemented fully in parallel with T5 — they only need to agree on the
  shape of "a string of system instructions goes in."

## Blocked / notes (updated during implementation)

- **T16 known gap, to be closed by T18:** `Apin/ApinApp.swift` still builds its `ModelContainer` at the default (per-target, private) location. T16 wired the widget extension's own `ModelContainer` to a shared App Group store (`group.com.apin.app`, `ApinJournal.sqlite`, entitlements added to both targets in `project.yml`) but explicitly did not touch `ApinApp.swift` (out of its scope). Until `ApinApp.swift`'s `ModelContainer(for: JournalEntry.self)` is replaced with a `ModelConfiguration(url:)` pointed at the same App Group container/filename, the widget will only ever see an empty store. T18 (CloudKit sync) already needs to touch `ApinApp.swift`'s `ModelConfiguration` — fold this App Group fix in there rather than a separate task, since both are the same file/concern (where the SwiftData store physically lives).
- **iCloud Drive conflict-copy risk:** this repo lives under `~/Documents/...` (iCloud Drive). Running 3+ task-runner agents fully in parallel touching nearby files produced iCloud "conflicted copy" duplicate files (` 2.swift`) and duplicate `.xcodeproj` bundles in one earlier wave — cleaned up. Mitigation going forward: cap parallel task-runners at 2 per wave, keep them in clearly separate folders/targets, and sanity-check for numbered-duplicate files after each wave before trusting a build.
- **T19 correction — assumed T3 copy-provider test did not actually exist:** T19's task description referred to "a structural copy-provider test for this already, from T3" in `ApinTests`, implying `CapabilityStatusCopyProviderTests` already existed and just needed to keep passing. It did not exist in the repo (T3's own acceptance criteria only required manual verification, not a unit test).
