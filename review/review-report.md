## Architecture check

Checked against `planning/engineering-plan.md`'s "Architecture decisions" section.

- **`ApinCore` never imports SwiftUI/UIKit — holds project-wide.** Verified with
  `grep -rn "^import SwiftUI\|^import UIKit" ApinCore/Sources/` → zero matches. (An
  unanchored grep for the substring "UIKit" alone matches every file's own
  "must never import SwiftUI/UIKit" header-comment reminder — using an anchored `^import`
  pattern to avoid that false positive is what actually confirms the rule holds.)
- **MVVM within `Features/`** — followed. `AskViewModel` (`@Observable`, `@MainActor`)
  cleanly separates state/transitions from `AskView`; `JournalListView`'s filtering state
  lives in the view itself (no separate `JournalListViewModel`), which is consistent with
  the plan's own carve-out ("SwiftUI views are not required to have tests unless they
  contain non-trivial logic (e.g. a view model)") — `JournalQuery.search(...)` is where the
  actual logic lives, and it's independently unit-tested (`JournalQueryTests`), not
  buried in the view.
- **`Core/AI` and `Core/Persistence` (here: `ApinCore/Sources/AI`,
  `ApinCore/Sources/Persistence`) are dependency-free-of-UI** — confirmed by the import
  grep above.
- **Testing strategy followed**: AI response *content* is untested anywhere (verified —
  `AssistantSessionServiceTests`/`FakeLanguageModelSession` exercise error-mapping and
  streaming plumbing only, never asserting on generated text). Deterministic logic
  (capability gate, repository CRUD/query, personality prompt *structure*, export writer,
  day-grouping) all has passing unit tests, matching the 74 `ApinCoreTests` +
  26 `ApinTests` + 7 `ApinWidgetTests` = 107 tests observed.
- **SwiftLint config matches the proposal**: `.swiftlint.yml` sets `line_length: 120`
  (warning tier) and opts into `trailing_closure` — matches the plan's "Swift defaults +
  `line_length: 120` (warning), trailing closures preferred" wording exactly. 0 violations
  currently.
- **Two intentional, well-documented deviations from the plan's literal architecture
  wording** — both functionally satisfy the plan's underlying *rationale* (no duplicated
  ask/save logic, no drift between entry points) via a different mechanism than the plan's
  bullet literally describes, and both are clearly explained in-code:
  1. *"App Intents and widget code live in the shared `ApinCore` package"* (plan, line
     108–111) — in practice, `AskAndSaveService`/`AskAndSaveServicing` (T8, the actual
     "ask → save" orchestration) live in the **app target**
     (`Apin/Features/Ask/AskAndSaveService.swift`), not `ApinCore`, because they depend on
     `AssistantSessionProviding`, itself intentionally app-target-scoped. T13/T17 reach the
     same flow indirectly (deep-link → `AskView` → `AskViewModel.submit()` →
     `AskAndSaveServicing`) rather than calling a shared `ApinCore` service directly. This
     matches `tasks/task-graph.md`'s own T13/T17 task-level scope ("deep-link only, do not
     duplicate ask/save logic") but is a real, if reasoned, drift from the plan's
     higher-level architecture bullet. `AskAndSaveService.swift`'s header already flags
     this explicitly and says a future task would need to relocate this orchestration into
     `ApinCore` if an inline (T15-style) App Intent ever needs to call it without going
     through the UI. **Recommend this be written up as an ADR** during `/remember` so the
     plan's stated architecture and the as-built one don't silently diverge for future
     cycles.
  2. `AskApinShortcutsProvider` (the `AppShortcutsProvider` conformance registering
     `AskApinIntent`) lives in `Apin/AppIntents/`, not `ApinCore/Sources/AppIntents/`,
     for a documented, empirically-verified technical reason (`AppShortcutsProvider`
     doesn't carry the `@_alwaysEmitConformanceMetadata` attribute needed for

     boundary — the intent itself, `AskApinIntent`, does carry it and correctly stays in
     `ApinCore`). This is a narrow, single-file exception, not a pattern that spread
     further. **Also worth an ADR** — this is exactly the kind of "hit a real SDK
     constraint mid-implementation" note `memory/adrs/` exists to capture so a future task
     doesn't re-discover it the hard way.

## Re-verification of self-reported items (not taken on trust)

1. **T18's removal of `@Attribute(.unique)` from `JournalEntry.id` + property-level
   defaults** — read `JournalEntry.swift` in full. Confirmed: `@Attribute(.unique)` is
   gone, and every stored property (`id`, `question`, `answer`, `createdAt`, `tags`) now
   has an inline default value, which the file's own comment correctly explains is a hard
   requirement for Core Data's CloudKit-mirroring delegate to materialize incoming records
   without routing through the custom `init`. This is accurate and necessary — Apple's
   CloudKit mirroring genuinely does not support unique constraints on `@Model` properties.
   **Risk assessment**: in practice, no code path in this codebase constructs a
   `JournalEntry` with anything other than a fresh `UUID()`, so duplicate `id`s won't occur
   through normal use today. But removing the constraint does mean **the database itself no
   longer enforces uniqueness** — if a future task (e.g. an import/restore feature, or a
   CloudKit conflict/merge edge case) ever produces two entries sharing an `id`,
   `fetch(by:)`/`delete(id:)` (which both call `.first` on a predicate match) would
   silently operate on only one of them, potentially leaving an orphaned duplicate behind
   after what looks like a successful delete. This is a reasonable, currently low-risk
   trade-off correctly forced by CloudKit, but it removes a safety net that used to exist
   for free — **recommend a `memory/technical-debt.md` entry** (not a defect requiring
   rework) capturing "no DB-level uniqueness guarantee on `JournalEntry.id` post-CloudKit;
   revisit if any future feature can produce/import entries with a caller-supplied `id`."
2. **T18's non-addition of `UIBackgroundModes: [remote-notification]`** — confirmed
   genuinely absent: not in `project.yml` (grepped, zero matches for `UIBackgroundModes`),
   and there is no hand-maintained `Apin/Info.plist` to check separately (the app target
   uses `GENERATE_INFOPLIST_FILE: YES`, so `project.yml` is the only place this could be
   configured). This is real, concrete follow-up work, not an oversight buried silently —
   T18's absence of this key was also independently corroborated at runtime: the
   `xcodebuild test` run above logged CloudKit's own diagnostic, `"CloudKit push
   notifications require the 'remote-notification' background mode in your info plist"`.
   Foreground CloudKit initialization/tests still pass, consistent with T18's own claim
   that only *background push-triggered* sync is affected. Recommend this be logged as a
   named follow-up (technical debt or a small future task) rather than left only as a
   comment, since it's an easy one-line fix (`project.yml`'s `Apin` target settings need
   `INFOPLIST_KEY_UIBackgroundModes: [remote-notification]` or equivalent) once someone
   picks it up.
3. **T13's "auto-submit on deep-link" UX decision** — confirmed clearly documented in
   `AskView.swift`'s file header (lines 14–24), including the explicit rationale (a
   Spotlight/Siri query already represents a fully-typed question; requiring an extra
   manual tap would be a worse UX for satisfying Req 5's baseline) and confirmation that it
   still routes through the exact same `AskViewModel.submit()` path a manual tap would.
   This is a legitimate product/UX judgment call worth Kv's second opinion (not a defect) —
   flagging for `/qa`'s manual pass and for `memory/decisions.md` to record once confirmed
   either way.
4. **"Zero network requests" manual-verification gap** — **partially, not fully,
   consistently flagged**. `AskApinIntent.swift` and `ApinWidgetEntryView.swift` both state
   "makes zero network requests" as an accomplished fact in their header comments (true and
   trivial for those two specific call sites, since neither actually invokes the model —
   they only hand a query to the deep-link coordinator). However, **the actual
   model-invocation path** — `AssistantSessionService.swift` (T4) and
   `AskView.swift`/`AskViewModel.swift` (T7), which is where this Definition-of-Done item
   actually matters — contains **no in-code note at all** acknowledging that this can't be
   verified in a headless/CI environment and needs a manual Instruments/network-conditioning
   pass. `memory/technical-debt.md` and `memory/decisions.md` are both still empty, so
   there's nowhere else in the repo this open item is currently recorded either. This
   isn't a functional defect (FoundationModels is genuinely on-device-only, and nothing in
   the code path constructs a `URLSession`/network call), but it **is a documentation gap**:
   the plan's Definition of Done explicitly calls this out as "safety-critical to the
   product's value proposition" and something `/qa` should spot-check — right now nothing
   in-repo flags it as still-open for that spot-check to happen against. **Recommend**
   `/qa`'s report explicitly carry this as an open manual-verification item, and that
   `/remember` add a `memory/technical-debt.md` entry so it isn't lost after this cycle.
5. **T14's `JournalEntryDeleteSideEffect`** — confirmed structurally consistent with T12's
   `JournalEntrySaveSideEffect` pattern (see API compatibility section above for the exact
   comparison) — same `Sendable`, non-throwing/best-effort contract, same
   "append-to-array, don't special-case" extension pattern, with one clearly-justified
   isolation difference. Not a one-off divergent design.
