  `-configuration Release` `xcodebuild build` succeeds cleanly, confirming
  `AskViewModel.resolvedCapabilityGate()`'s Release path falls through to `CapabilityGate.live()`
  unconditionally with no compile-time dependency on the debug-only type.
- **App Group / CloudKit architecture (`group.com.apin.app`, `ModelConfiguration(cloudKitDatabase:
  .automatic)`, ADR-002) is unchanged and, per the fix verified above, now actually internally
  consistent** across `project.yml`, both entitlements files, and both Swift-source literals —
  this cycle's changes strengthen rather than weaken ADR-002's stated guarantee.
- **`ApinCore` never imports SwiftUI/UIKit** — reconfirmed with the anchored
  `grep -rn "^import SwiftUI\|^import UIKit" ApinCore/Sources/` check from
  `memory/coding-standards.md`: zero matches, including the two new `ApinCore/Sources/` files
  added this cycle (`CapabilityGateDebugOverride.swift`, `JournalDigest.swift`).
- **T11's tag-filter design is a real, verified, load-bearing finding, not an assumption, and it's
  applied consistently at both call sites.** `JournalQuery.tagFilter`'s doc comment documents a
  direct reproduction: `entry.tags.contains(_:)` inside `#Predicate` segfaults the process at
  fetch time, and `entry.tags.contains(where:)` throws `NSInvalidArgumentException: "Can't have a
  non-relationship collection element in a subquery"` — both confirmed as a genuine Core Data
  SQL-store limitation on `JournalEntry.tags`'s transformable-attribute storage shape, not a bug
  guessed-around. The resulting design (`JournalQuery.tagFilter` as a separate in-memory
  post-fetch filter, applied via `JournalQuery.applyTagFilter(to:)`) is applied identically at
  both call sites — confirmed by reading both: `SwiftDataJournalRepository.fetch(matching:)`
  calls `query.applyTagFilter(to: results)` after the SwiftData fetch, and
  `JournalListView.JournalEntryListContent.entries` (a computed property) calls
  `query.applyTagFilter(to: queriedEntries)` on the `@Query`-fetched array — same rule, same
  order of operations, both documented as deliberately sharing this exact function so the two
  call sites "can't drift." `JournalQueryTests.swift` covers tag-only, exact-vs-substring, and
  AND-combined-with-keyword/date-range cases against a real in-memory `SwiftDataJournalRepository`.
- **Folder-by-feature convention followed for new UI**: `Apin/Features/Digest/WeeklyDigestView.swift`
  (T12, new feature folder, matches the convention's own suggested naming) and
  `Apin/Features/Journal/JournalTagFilterView.swift` (T11, existing folder). Digest/streak
  computation logic (`JournalDigest.compute(from:)`) correctly lives in
  `ApinCore/Sources/Persistence/` as a plain, non-SwiftUI-importing testable type rather than
  embedded in the view, per the plan's explicit instruction and `memory/coding-standards.md`'s
  "extract non-trivial logic out of the view" rule.

No architecture-inconsistent decisions found anywhere in the combined diff.
