  guardrail-refusal mapping onto the new structured entry point). Read directly — structurally

- T3: `JournalExcerpt.firstSentence(from:)` — 8 new tests in `JournalExcerptTests.swift` (matches
  the task graph's claimed count exactly: empty/blank, single-sentence, multi-sentence boundary,
  sentence-less fallback, and edge cases per the file's documented rule).
- T4: `AskAndSaveService`'s `autoTags` seeding — 2 new tests in `AskAndSaveServiceTests.swift`,
  both `#if canImport(FoundationModels)`-gated, read directly (not just trusted from the name):
  - `testSuccessfulStructuredCallSeedsSavedEntryTags` — asserts a successful
    `structuredBehavior` maps its `AskResponse.tags` onto the saved `JournalEntry.tags` exactly.
  - `testFailedStructuredCallSavesEntryWithEmptyTagsAndDoesNotFailTheStream` — asserts a
    `.failure(...)` `structuredBehavior` still yields the full stream, still saves exactly one
    entry, with `tags == []`, and the stream does not throw.
  Cross-checked against `AskAndSaveService.autoTags(from:prompt:)`'s actual implementation: the
  `#if canImport(FoundationModels)` gate gives `.failure` → `[]` (never propagates/throws) and the
  `#else` branch (no FoundationModels) also returns `[]` unconditionally — the primary answer
  save genuinely cannot fail because of this call, confirmed by reading the source, not inferred
  from the doc comment alone.

**New code with no test coverage, and why:**
- **T1's `Apin/DesignSystem/*` token layer** (`ApinColor`, `ApinFont`, `ApinIcon`, `ApinRadius`,
  `ApinSpacing`) — no unit tests. These are flat constant namespaces with no branching logic to
  test (a `Color`/`Font`/`CGFloat` literal either has the right value or it doesn't, and nothing in
  `memory/coding-standards.md`'s testing section requires tests for constant declarations); the
  OKLCH→sRGB conversion *arithmetic* was spot-checked by `/review` against an independent
  from-scratch implementation (4 of the converted constants matched to 4 decimal places) rather
  than unit-tested in-repo, which is a reasonable call for a one-time, source-commented conversion
  with zero runtime computation. Zero consumers this cycle, so no integration risk either.
- **T5's root-navigation composition** (`ContentView.swift`'s `TabView`, sibling
  `NavigationStack`s, `.badge(_:)` wiring) — no automated tests, and this is a **deliberate,
  convention-driven gap, not an oversight**: `memory/coding-standards.md`'s Testing section states
  "SwiftUI views are not required to have tests unless they contain non-trivial logic (e.g. a view
  model, or a testable query-builder function extracted out of the view)." `ContentView.swift`
  contains no such extractable logic — it's pure view composition (`TabView` + two child views +
  a `@Query`-driven `.badge`). The one piece of this task's surface that *is* logic-bearing and
  regression-sensitive (whether the deep-link flow still reaches `AskViewModel`) is covered
  indirectly via `AskDeepLinkCoordinatorTests` (6/6, `ApinCoreTests`) plus the direct trace of
  `AskView.swift`'s unchanged `.onAppear`/`.onChange` wiring documented in Regression results
  above — not a SwiftUI-view test, but the closest thing to one this project's own conventions
  call for. No XCUITest exists for the actual tab-switching/navigation behavior (XCUITest is
  explicitly optional/deferred project-wide per coding-standards) — this means the "no duplicate
  nested `NavigationStack`" and "journal button reachable" acceptance criteria are verified by
  build success + code reading in this sandbox, not by an automated or manual on-device
  click-through, since the app can't launch here (App Group crash). This is the one item in this
  cycle's Definition of Done that is **compile-verified, not behavior-verified** in this
  environment — flagging explicitly rather than blurring it into "tested."
